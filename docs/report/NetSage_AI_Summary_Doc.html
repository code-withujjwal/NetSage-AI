01 · Executive Summary

NetSage AI is an advanced, AI-assisted network troubleshooting engine designed to accelerate fault isolation and resolution in enterprise environments. The system leverages Google Gemini to process symptom descriptions, network topologies, and Cisco show command evidence to generate accurate, actionable diagnoses — all governed by a strict human-in-the-loop review workflow and Responsible AI framework.

02 · Problem Statement

Identifying root causes of network disruptions involves manually parsing extensive device logs and configuration outputs. Junior engineers frequently struggle to correlate symptoms (e.g., unreachable gateways) with the underlying CLI evidence (e.g., misconfigured VLANs or missing ACLs). Relying solely on manual analysis increases MTTR and operational overhead. Conversely, relying entirely on unfiltered generative AI introduces the risk of "hallucinations" and unverified configuration changes.

03 · Objectives
  • Accelerate Fault Diagnosis: Build an AI pipeline capable of rapidly analyzing Cisco show command outputs to identify network faults.
  • Ensure Deterministic Reliability: Implement pre-screening rule checks to statically validate common misconfigurations prior to AI processing.
  • Maintain Responsible AI Standards: Enforce a strict human-in-the-loop workflow where all AI-generated diagnoses are treated as advisory and require human review.
  • Provide Actionable Insights: Present diagnosis, evidence, and review logs in an interactive, user-friendly Streamlit dashboard.

NetSage AI follows a modular, decoupled architecture with five layers:

  1. Frontend (Streamlit): Interactive dashboard for case metrics, AI performance, and the review audit trail.
  2. Backend (FastAPI): High-performance REST API that orchestrates incoming case requests.
  3. Deterministic Rule Checker: Python-based regex validation that scans evidence for explicit configuration violations.
  4. AI Diagnosis Engine (Google Gemini): Generative AI module with strict system prompts and Pydantic-validated structured JSON output.
  5. Human Review / RAI Logger: Governance module that logs human decisions alongside AI confidence scores.

07 · Hybrid Analysis Workflow

7.1 Deterministic Rule Validation

Incoming cases are first processed by a deterministic rule-checking algorithm using regex-based static analysis to identify glaring misconfigurations — such as subnet mask mismatches or administratively down interfaces — providing a highly reliable, zero-hallucination baseline.

7.2 AI Diagnosis Workflow

Cases requiring deeper logical correlation are processed by Google Gemini. The AI is constrained by a highly structured system prompt, instructing it to act as a senior network engineer. It is strictly mandated to base conclusions entirely on the provided CLI evidence, outputting a structured JSON response containing: root cause, suggested fix commands, and a calculated confidence score.

08 · Responsible AI Framework
  • Human Oversight: AI outputs are strictly advisory. Operators must Accept, Edit, or Reject every diagnosis before any fix is applied.
  • Audit Logging: Every interaction is recorded in responsible_ai_log.csv, tracking AI uncertainty and human corrections.
  • Evidence-Based Constraints: The AI outputs "Insufficient Evidence" if show commands do not prove a fault.

09 · Testing & Results

The system successfully processed the 30-case troubleshooting dataset. The hybrid architecture proved highly effective: the deterministic rule checker reliably acted as a safety net for basic configuration flaws, while the Gemini engine accurately diagnosed complex, multi-variable issues. Pydantic validation ensured the AI consistently returned correctly formatted JSON data.

10 · Project Limitations
  • Packet Tracer Deliverables: While the text dataset covers 30 cases, only one corresponding Packet Tracer topology (NetSage-AI-VLAN-001.pkt) is provided as a demonstrated simulation artifact.
  • API Constraints: Intermittent Gemini API quota limitations required deterministic fallback logic. Cases processed by fallback are explicitly labeled [DEMO FALLBACK].
  • Static Evidence: The system analyzes static, pre-collected CLI text rather than live SSH connections to networking hardware.
11 · Future Scope
  • Direct SSH/Netmiko integration for live show command collection from Cisco devices.
  • Integration of a local, open-source LLM to resolve external API quota dependencies and improve data privacy.
  • Expanding the dataset to cover BGP, MPLS, and SD-WAN troubleshooting scenarios.
